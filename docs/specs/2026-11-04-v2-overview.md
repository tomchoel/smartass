# smartass v2: overview

Status: draft for review (2026-11-04). Decisions taken with Tom in the v2 brainstorm on 2026-11-04.
Sub-specs: [1 Engine](2026-11-04-v2-1-engine-design.md) · [2 Knowledge](2026-11-04-v2-2-knowledge-design.md) ·
3 Excel panel (later) · 4 Distribution and stewardship (later).

## Why v2

v1 works, but it grew layer on layer: a regex gate that silently picks the wrong analysis ("plan" means budget),
recipes running on a legacy `templates.py` through stub objects, the P&L computed three times (analytics, spec
evaluator with `eval`, Excel formulas), values checked by reading Excel back, 2 MB of hand-approved JSON maps,
~23k tokens of skill text, and 25 tools. It is too heavy for colleagues and too fragile to grow.

## Goal and success criteria

Tom and colleagues in Telenor Norge Finance use it actively for everything Finance does: ad hoc questions and
extracts, monthly packs, variances down to ledger lines, and inputs to Produktregnskap / Nkom models and decks.

v2 is done when, on a test set of 20–30 real questions (B01–B16 plus new ones) with golden numbers and a rubric
approved by Tom and 1–2 controllers:

1. **Right numbers, always.** Every number matches the golden value and reconciles to the cube; zero silent errors.
2. **Controller-level insight.** The critic scores every answer at least 4 of 5 on the rubric, and the
   approved golden answers are matched.

Speed and ease of install matter but are not gates.

## Decisions

| # | Decision |
|---|---|
| D1 | Clients: an Excel task pane (primary) and the CLI, over the same engine. Client-neutral: Claude or Copilot (licence not settled). |
| D2 | Scope: everything above; Prodreg/Nkom and decks are integrations (prodreg catalogue, tn-deck), not core. |
| D3 | A new slim core in the same repo, built beside v1. Proven parts (Smart View HTTP protocol, sign-in, atlas, drill, styles, formula checker, snapshots) are lifted in. v1 is deleted in one PR once v2 passes the test set. |
| D4 | The model interprets the question; the engine validates. The regex gate and fixed recipes go. |
| D5 | A **finance agent** steers the analysis: plan → build → critic. Quick ad hoc answers skip the critic. |
| D6 | The agent writes a **free spec of typed blocks** (table, bridge, trend, ranking, KPI tiles, matrix, drivers, commentary). Every number on the sheet is a live formula on the source data; nothing is hard-coded. |
| D7 | Python computes every value from one model; Excel displays it with formulas. Reading the sheet back is only a check that sheet = model. |
| D8 | Fetched data lands in **one long Excel table per question** (`Data_Q<n>`); formulas are SUMIFS/XLOOKUP on labels (tn-formelstil). |
| D9 | Guards: **hard on data** (unknown members or metrics, open month unmarked, totals not reconciling to the cube, wrong sign → stop); **soft on method** (no last year, no top-N + Other, no source → critic warns). |
| D10 | Data channel behind one `Provider` interface: Smart View HTTP now (ad hoc grid in Excel as fallback); EPM REST (and an ERP report for ledger lines) plugs in when Tech grants access. BigQuery is out of v1. |
| D11 | smartass owns data, answers, snapshot/revert, TN format and the formula check. Excel MCP does every other Excel job (read, write, pivots, Power Query, charts, closed files), after a smartass snapshot. |
| D12 | Monthly packs are saved specs in the workbook with relative periods; one click refreshes them to the latest closed month without AI. AI only writes the commentary. |
| D13 | Knowledge: a typed, executable **semantic layer** + **just-in-time caveats** in tool replies + **time-valid facts** + delivery **through the MCP server** (tools, resources, prompts) + **eval-gated** changes + **automatic answer memory**. No vector store. Nobody enters data by hand month to month. |
| D14 | Knowledge is **refreshed every month** automatically after close: atlas rebuild, diff, impact report, eval run; only new or changed items need Tom's one-time approval. |
| D15 | Insight comes from the data: the engine decomposes every material variance down the next dimension (and to suppliers / ledger lines by drill) and returns the evidence. Commentary basis is `data` or `hypothesis`. |
| D16 | Stewardship: Tom (+ one backup) owns code, releases and knowledge approval. Releases are versioned and hash-checked. |

Dropped in the brainstorm: an event register and a commentary memory that people maintain by hand (nobody enters
anything), BigQuery in v1, LAMBDA-named formulas, a shared pull cache.

## Shape

```
 Excel pane / CLI (Claude or Copilot)
        │  MCP
        ▼
 smartass v2 server ── tools (8) · resources (playbooks, conventions) · prompts (plan, critic, monthly pack)
   ├─ knowledge   knowledge.db: atlas + semantic layer + facts + aliases (FTS) · answers.db (per user)
   ├─ model       AnalysisSpec → queries → facts frame → blocks → expression trees → values, checks, drivers
   ├─ data        Provider: SmartViewHttp | AdhocExcel | (EpmRest later) · drill (FinLite lines)
   ├─ render      expression trees → Excel formulas on Data_Q<n>, TN style, charts, sheet order, sheet = model
   └─ runtime     hidden Excel host, user Excel attach, snapshots, relay, logs, health
 Excel MCP ── every generic Excel job, after xl_snapshot
```

## Build order

1. Sub-spec 1, engine: model, data, render, runtime, tools. Passes B01–B16 numbers.
2. Sub-spec 2, knowledge: semantic layer, caveats, monthly refresh, playbooks, critic. Passes the rubric.
3. Sub-spec 3, Excel pane (needs IT for add-in deployment; start that conversation early).
4. Sub-spec 4, distribution and stewardship (installer, signed releases, backup owner, colleague onboarding).

Sub-specs 1 and 2 can run in parallel once the `AnalysisSpec` and `fin_lookup` contracts are fixed (in spec 1).
