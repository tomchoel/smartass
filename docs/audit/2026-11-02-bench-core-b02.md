## Walking-skeleton result

B02 (Business Norway EBITDA per month 2026 vs 2025, reconciled to YTD) runs end-to-end on the new core
(`sv_answer`, answer spec v1): scope (gate `clear`) → pull (two HTTP grids) → answer (skeleton sheet first,
one-block render, stored spec) → check. Both source grids fetched over the Smart View **HTTP** provider; every
derived cell is an Excel formula into them; the three oracle values (EBITDA YTD Sep 26, Sep 25, Jun 26 periodic
for un.SY.2BUS) all appear, every reconciliation check is OK, and there are no formula errors.

Timing: first visible output 28.06 s, total 56.22 s (rerun 13:10 after the cleanup fix: 21.05 s / 50.83 s, PASS). Both are dominated by the one-time cold start (hidden Edge +
SSO + three cube sessions + Excel), measured in R2 at 13–26 s and here ~28 s; the warm pulls are ~0.4 s and the
one-block write ~0.2 s (R2, R3). A second answer in the same session reuses the warm engine.

## Baseline comparison (blocked by the COM path's known weakness)

The baseline route (`--route baseline`, `sv_ws_build` → HsGetValue grids in Excel's own Smart View) could **not**
run on 2026-11-02: every FinMax connect returned "Empty response from provider" and no Smart View Login appeared —
the stale shared-WebView sign-in documented in R1 (`docs/archive/audit/2026-11-02-risk-spikes.md`) and `docs/troubleshooting.md`. It
persisted across Excel restarts because the WebView cookie store is shared; the documented fix (rename the Smart
View cookies) logs the user out of Smart View, so it was not applied. The core route was unaffected: it uses its
own hidden Edge SSO, independent of Excel's Smart View. This is itself a point for the HTTP core path.

(`docs/plans/2026-11-02-walking-skeleton.md`, "Measured today").
